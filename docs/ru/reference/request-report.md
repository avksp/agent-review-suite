# Контракты ревью v1

[English](../../reference/request-report.md)

MUST означает обязательное требование, а MUST NOT означает запрет.
SHOULD означает рекомендацию, отступление от которой требует основания.
MAY означает разрешение. Эти значения применяются к терминам в верхнем
регистре. Правило определяют [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)
и [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

Вызывающая сторона обязана (MUST) передать доверенные ожидаемые привязки
отдельно и защитить их от авторов запроса или отчёта. Она управляет сбором
данных, актуальностью исходников, назначением ревьюверов и приёмкой. ARS
читает ссылки на файлы и инструкции в данных ревью как текст.

## Файлы схем

Каждая схема использует [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12).
Схемы описывают отдельные разобранные документы JSON.

| Документ | Требуемый `schemaVersion` | Содержимое |
| --- | --- | --- |
| [Запрос](../../../schemas/review-request.v1.schema.json) | `ars.review-request.v1` | Привязки, область, роль и обязательные ID покрытия |
| [Отчёт](../../../schemas/review-report.v1.schema.json) | `ars.review-report.v1` | Привязки, хеш запроса, состояние выполнения, покрытие, замечания, доказательства, расход и ограничения |
| [Ожидаемые привязки](../../../schemas/review-expectations.v1.schema.json) | `ars.review-expectations.v1` | Доверенные привязки, хеш точных байтов запроса и обязательные ID покрытия |

## Проверки при выполнении

Валидатор проверяет исходные байты, правила записей и совпадение с
доверенными привязками. Вход обязан (MUST) быть JSON в UTF-8 без BOM,
повторных ключей, бесконечных и неопределённых чисел или одиночных суррогатных кодовых
точек. Предел каждого входа составляет 262144 байта и 32 уровня контейнеров.
Идентификаторы должны (MUST) быть уникальны внутри своего множества.
Например, две записи пакетов с одинаковым ID могут пройти проверку структуры.
Валидатор отклоняет их.

Привязки включают ID запроса и назначения, ID исходников и базовой версии,
представление исходников, хеши SHA-256 исходников и базы, а также точное
множество ID, версий и хешей пакетов. V1 поддерживает `git-diff-bytes-v1` и
`source-bundle-bytes-v1`. Вызывающая сторона хеширует собранные байты.
Форматирование запроса меняет его хеш. Порядок пакетов не влияет на сравнение
множеств. Происхождение и актуальность байтов проверяет вызывающая сторона.

В отчёте `COMPLETE` все строки покрытия должны (MUST) быть отмечены как
проверенные. В `INCOMPLETE` должна (MUST) быть хотя бы одна непроверенная
строка. Отчёт `FAILED` может (MAY) сохранить наблюдения. Множество ID
покрытия обязано (MUST) совпадать с доверенными привязками. Пределы отчёта
составляют 1000 замечаний, 2000 строк доказательств и 2000 ссылок от
замечаний к доказательствам. Для каждого замечания указывают степень
подтверждения. ID доказательств должны (MUST) ссылаться на строки доказательств в отчёте.
Доказательства оценивает вызывающая сторона.

Неизвестный расход должен (MUST) остаться `null`. Ноль означает измеренное
значение. Известный расход задают ограниченными неотрицательными целыми
числами. Валидатор проверяет точные числовые значения. Например, `1.0`
имеет целое значение 1. Дробное значение не проходит проверку.

## Результат

```python
from agent_review_suite.contracts import validate_bytes

report = validate_bytes("report", report_bytes, trusted_expectations_bytes)
status = report["executionStatus"]
```

Например, корректный по форме отчёт с подменённым ID покрытия даёт ошибку
`binding-mismatch`. Повторная строка покрытия в том же отчёте даёт сначала
`malformed`. После успешной валидации вызывающая сторона читает состояние
выполнения ревью и решает, как использовать замечания.

См. [учебный пример](../tutorials/first-validation.md) и
[проверку ограниченного ввода CLI](validation.md).
